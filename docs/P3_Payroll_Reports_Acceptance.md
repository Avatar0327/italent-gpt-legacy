# 薪酬批次办理与已发布工资对账

2026-09-07；基于本系统既有核定工资及补差模型独立实现，未宣称复现原系统未核实报表规则。

| 维度 | 证据 |
|---|---|
| 需求 | 已有本地工资批次与补差生命周期；企业正式报表口径仍待核实 |
| 开发 | payrollOperations、payrollReconciliation，薪酬工作台入口及审计CSV导出 |
| 测试 | 新增2项集成场景，全套P3 72项通过，类型检查及构建通过 |
| 生产验收 | 未完成；不含银行对账、付款、税费计算和企业UAT |

批次办理保留草稿、待复核、已批准、已发布及取消状态，逐批列示非取消明细金额；这些金额不能跨状态直接当作正式工资加总。已发布对账逐工资条呈现原金额、已发布补差、两者合计，四类金额为应发、扣款、净额及单位承担，单位人民币分。补差次数按已发布记录计，冲减保留负号，不新增原工资条。员工信息为工资编制时快照，组织授权按当前账号可管理的批次组织校验。

服务端仅允许admin/payroll_editor/payroll_reviewer。特别验证：被关联为员工且在其他组织任薪酬编制岗时，本人工资可自助查看，但不会因此出现在无该组织授权的管理报表。HR、经理、普通员工被拒绝。来源材料与审批证据不进入报表。

验证覆盖：批准未发布不计入；正负补差及冲减整数分相抵；取消明细、取消批次；期间关键词与分页；过期版本导出冲突；审计失败不返回CSV且修订号不变；CSV公式前缀防护。测试数据全部为合成。

## 本地计算量优化
薪酬报表提前进入专岗范围校验与索引分组计算，避免先做无用的通用权限投影及为每条工资重复扫描批次/补差。2000、4000、8000条合成工资（各有补差记录、含范围外及取消/未发布记录）两类报表的标题/列/行哈希均与优化前一致。每种规模预热1次、计时3次取中位数；8000条对账由2993.22ms降至90.80ms，批次办理由1277.43ms降至9.65ms。机器负载/JIT/GC会影响结果，不能换算线上吞吐。详细数据见Payroll_Report_Benchmark.json，可用node scripts/benchmark-payroll-reports.mjs复测当前版本。数据库、网络、CSV、跨账号并发及恢复尚未纳入测量；P3功能回归仍78项，不把测量次数增加为功能场景。

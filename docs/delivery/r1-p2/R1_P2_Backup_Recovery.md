## 一致恢复点：基线、增量日志和不可变附件

推荐方案A为“每日完整逻辑导出＋15分钟增量归档＋不可变对象清单”，可选Time Travel作额外补救；不以其原地恢复替隔离还原。满足条件前 `backupCapability=not_verified`，由平台负责人在P3技术任务确认：实际计划、导出/导入接口、隔离DB与R2目标、受控定时执行、独立凭证/密钥/告警通道。现有Sites声明只有DB/BUCKET，未出现这些配置；本轮不创建资源、不扩大权限。

每个恢复单元 `checkpointId` 包含：源码完整SHA、依赖锁文件/DDL清单及hash、schemaVersion/epoch、DB基线file/chunk列表及hash、每租户sourceRevision、增量seq范围及前块hash、R2对象key/versionId/length/MIME/SHA256/归属/tombstone、最早/最晚有效恢复时间、keyId、manifestVersion/digest/signature、securityLedger水位引用和执行/复核回执。

1. 所有业务/授权/附件元数据写入在同一D1事务追加**完整行变更日志** `recovery_change(tenant,seq,txId,table,key,op,afterImage,schemaVersion,digest)`，与业务事件outbox分开。业务事件只说“已生效”不足以恢复所有列，不能拿outbox代替DB增量。事务边界不可拆；schema变更有独立版本日志。全站共享表的R2/R3写入也必须经桥接闸门，覆盖不了就不能宣称全库增量可恢复。
2. 每日基线：持久写闸门与fence令所有写入口拒绝新提交，待当前事务结束；记录租户revision水位；执行一致SQL导出并核导出包含该水位。获得固定导出后解除写闸门，后续上传可异步。export停顿实际>允许窗口时采用经过验证的MVCC逻辑版本导出或方案B，不静默长停。当前版本尚无完整行日志/MVCC，列为待新增。
3. 附件put使用不可变key，D1成功引用后才成为业务可读对象；物理删除必须检查所有未过期checkpoint引用。逻辑墓碑即时拒绝访问，字节按恢复依赖保留；30天恢复保留不恢复旧读权。孤儿无DB引用不作为业务文件恢复。
4. 每15分钟按已提交完整事务边界封存增量段至独立备份目标；最后选seq=S，导出对应引用集合。基线和增量中所有可达对象均已复制/校验后才发布manifest=verified。对象缺失、日志断序、事务半截、schema未知、hash不符均不能推进verified水位。已发布manifest不可覆盖。
5. 分块流式加密/上传，块默认≤4MiB，单对象可多块；读取与验证有界，不将1GB导出装进128MB Worker。AES-256-GCM每对象/块唯一nonce，AAD绑定checkpoint+chunk；KMS/密钥托管角色保管KEK，manifest含wrapped DEK及keyId，密钥与密文分离。验签公钥可用于独立复核；秘密不入Git、日志或下载链接。
6. 基线至少保留覆盖最老30天恢复点所需的前一基线，设计保留31个日基线＋30天增量；对象直到最后引用manifest过期再进入回收候选。密钥保留同样覆盖全部可恢复点。热D1日志可在归档验证并保留至少48小时热窗口后清理，清理依据已验证水位，**不删除业务历史/审计**；备份日志的30天副本继续保留。
7. 15分钟周期＋最多5分钟调度抖动＋最多20分钟封存/复制校验预算=40分钟健康恢复点年龄预算；45分钟预警、55分钟严重告警，超过60分钟记录目标违约。单次备份成功不等于整个30天持续满足RPO；连续监控verified时点。

## 隔离恢复状态机和当前授权对账

`incident_confirmed → isolated → source_verified → database_restored → objects_verified → authorization_reconciled → business_checked → owner_approved → opened`。每步写独立恢复回执；任何不确定回到blocked，不跳步。所有状态在恢复控制平面记录，不能只存在即将恢复的旧DB中。

独立可信当前授权来源设计为 `security_revision_ledger`，位于**不随业务DB回滚的受控安全存储/独立备份域**，且结合平台当前访问配置。它是安全事件证据，不是项目范围台账。保存tenant/user绑定、active、角色、scope/field/action grant摘要和撤销事件、单调revision、链式digest/签名。恢复旧DB不能覆盖这份记录。

权限变更采用保守协议：撤权/缩权先将deny及新securityEpoch持久化到独立安全服务，再改业务DB；授权扩大先完成业务DB和安全服务双方确认才激活。跨存储失败时默认deny，不冒充双库原子事务。请求/后台任务同步核当前securityEpoch和deny，不等异步消息才撤权。安全服务未知/不可达则受保护读写拒绝。对账恢复期按“当前平台访问 ∩ 当前可信安全授权 ∩ 恢复业务对象有效权”，不凭旧备份开通账号；新grant不能使恢复点不存在的业务对象出现。若安全日志断链或未证明足够新，保持隔离并由安全负责人修复。

隔离目标使用新DB/R2前缀/密钥及禁外发配置，平台入口、应用API、附件、job和适配器都受 `recoveryEpoch/openGate` 控制。恢复后原outbox暂停；独立保存的外部回执/发送水位用于防止恢复点后已执行交易再次发出。未知支付/签署/消息逐意图对账，禁止“把pending全重跑”。一级已办的D7节点不再执行，二级及HR执行需当前授权和批准有效条件；不能继承旧即时生效历史测试作为现规则证明。

这些是工程预算而非实测结果。DB 5GB在60分钟内至少1.39MB/s有效导入吞吐，另受SQL/索引/事务数量制约；附件100GB在60分钟内至少27.8MB/s，500GB至少138.9MB/s。只核带宽不核对象API吞吐不足：一百万个对象每秒100次校验需167分钟，因此需要已验证的并行度、流式内容校验和目标容量。隔离对象可先复制后逐hash核，但未完成关键清单核验前不开放。

当前真实DB大小、日变更量、附件数/分布、导入吞吐及平台额度没有取证，不能宣称目标“已经经济实现”。P3按小/中/压力档合成测量；P4按实际代表容量完成全链演练。若瓶颈超预算，提交下面备选和差额，不降低1小时/4小时/30天。
